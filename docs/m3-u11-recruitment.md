## 业务边界

Manager 通过 `inspect_candidate` 读取实际商业条款，在 `recruit` 决策中提出
`recruit_from_market`，Owner 再批准固定提案。工具同时要求 `approve_hiring` 和
`spend_credits`，支出授权按本次金额检查上限。两项权限是交集；普通写工具保留原有门禁。
执行前重查身份、任职、项目管理权、原批准人及会话、期限、两项 Authority，以及挂牌、
价格、交易模式和结算政策的版本。Agent 不能传入批准人或替换已批准的参数。

本工具只支持既有 M1 一口价交易。没有商业条款时拒绝，不推定免费；议价明确返回需要
卖方接受，不替卖方同意，也不偷偷创建待接受报单。人类既有 T2 / 议价入口保留，U26 再加固
其高影响入口。候选详情由 M1 服务组合 T2 的公开事实与价格白名单；T2 市场领域不增加经济依赖。
HTTP 与 Agent 共用此读面，不公开商业 metadata。

执行复用 `TalentTradeService → RecruitmentService → ProvisioningJob`，同一个事务保存
资金结算、雇佣、开通意图、成交来源事件及最终 ToolAudit。最终审计失败会一起回滚，已批准
提案仍可重试。来源事件在外层提交后才分发；跨进程未送达事件的补偿属于 U16。
并发抢同一人才最多成交一次，批准与请求重放均不重复扣款。招聘沿用原 Person，资产不复制。
Agent 发起者记录为 Employee，不能把 Employee ID 当作 User ID。

返回值分别记录招聘、已结算交易和开通状态。雇佣事务只产生待处理的开通意图，Docker /
Provider 调用发生在提交后。`inspect_readiness` 与 HTTP 就绪报告展示同一份开通 job 和分步原因；
开通 partial、模型不可用、尚无职位等事实都不能冒充可工作。系统不自动选择职位或分配任务。

## 真实验收

新增隔离集成场景使用固定 Hermes 镜像
`sha256:33a938c54ec8f58cd3128901b378c226b2846fde5f217533bdae2b1501bd26e5`。
真实模型依次读取项目、搜索人才、读取候选条款、提出招聘，并在收到 `confirmation_pending`
后结束管理会话。保留真实请求、结构化响应、Decision / ToolAudit 引用及运行出处。

测试随后建立实际 UserSession / OWNER membership，通过正式确认领域服务批准并执行，
没有让模型自批。HTTP 认证与 CSRF 由行为测试覆盖。一次明确的人类职位指派补充职位事实；
它不归功于 Manager。新员工完成实际 Docker 开通、控制面探测和新的付费模型探测，最终
`ready_to_work=True`。这里没有执行 Worker 任务或 Reviewer，U29 的招聘后交付验收仍待完成。
