U7 对话内部的绑定、投影和工具桥事务仍为同步操作。本批只关闭运行器自身的阻塞路径，
不声明整条请求链均已异步化。数据库锁等待仍受驱动设置约束。耗尽终态重试时没有伪造
数据库成功，`finalization_failures` 保留期望结果；跨进程接管与持久恢复继续归 U16。

扫描进度只优化发现过程，不能证明会话执行完成。`ManagementDispatch` 仍保存唯一来源
与会话关联，`WorkSession` 仍是执行状态来源。v55 的唯一应用进度写入者为
`management_dispatch.discover_sources`；SQLite 触发器只在低编号事件成为适用来源时回退
受影响范围的进度。直接领取较新的来源不会推进扫描游标，不会跳过更早来源。
回退后重读的已观察来源也不重新执行。原事件 ID 的既有处理历史不能改写或用于新执行。

## 升级与验证步骤

以下是本地 SQLite 部署的操作说明，尚未在开发或生产数据库执行。执行升级的维护者负责
备份、验证和恢复判断；生产历史规模与停机时间仍需在目标数据库上测量。

1. 停止服务及所有数据库写入者，保存数据库备份和当前 Alembic 版本。记录 WorkSession
   总数、最小/最大 ID，以及旧会话完整字段和被引用关系。仅比较数量不能证明历史保留。
   v53 之前不存在 `purpose`、`project_id`、`review_request_id` 会话列，升级前不要查询它们。
2. 在同版本隔离副本中先试运行升级。使用项目环境从 `apps/server` 执行
   `python -m alembic upgrade head`；本批 head 为 `55a104d932ef`，按 v53 → v54 → v55
   顺序应用。v53 重建会话表，使用迁移要求的独立连接和外键设置，勿手工绕过守卫。
3. 在重新允许新会话前，核对旧会话逐行字段、旧快照及原有引用关系，确认没有历史回填或丢失。
   运行 `python -m alembic check` 与 `PRAGMA foreign_key_check`，确认唯一 head、无模型漂移
   和无外键破损。检查 v53 四个会话触发器、v54 五个命名索引及十一个来源触发器仍存在，
   v55 新增游标表、`ix_events_management_discovery` 和两个 `management_discovery_rewind_*`
   触发器。临时库测试同时验证迁移建表与模型建表一致。
4. 运行器默认关闭。只在已配置明确的预算准入与逐轮限制后启用；单独打开开关不足以运行
   模型，没有预算钩子时应停在 `budget_unavailable`。恢复服务后观察首次历史补读完成，
   再核对至少一个管理来源和一个指定评审来源的唯一会话、实际动作审计和终态。
5. 对照 `management finalization failed` / `management finalization exhausted` 日志中的
   source/session ID 与数据库行。重试成功不应新增模型请求；耗尽时应有明确错误且其他
   生产者和事件引擎完成关闭。若出现同源重复会话、跨公司归属或无解释的历史变化，停止
   新准入并保留现场；不能通过删除来源历史或把 running 直接改为完成来恢复。
6. v55 进度可以重建，降至 v54 只失去扫描优化；消费历史保留。v54 有任何去重历史时拒绝
   再降，v53 有非 worker 会话时拒绝再降。优先向前修复；恢复备份需要另行确认备份后
   已发生的工作如何处理，不能删除记录以强行绕过降级保护。

本批没有推送、创建 PR、迁移开发数据库或改变已有用户容器。原始红绿日志保存在本次
