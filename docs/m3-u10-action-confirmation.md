## 固定提案与执行

具有 `ConfirmationPolicy` 的内部高影响工具可进入确认通道。策略明确决策类型、版本、
服务器端条款查询及有限期限；工具仍必须声明 Authority、项目、整数金额和 required 决策语义。
无策略的高影响工具、普通写工具和调试 CLI 保留既有门禁。默认期限为 1 小时，策略最多允许
24 小时；批准不会延长到期时间。

`ActionConfirmation` 保存原 Person / Employee / 公司、管理会话、项目、决策、运行请求与
动作序号、固定入参及摘要、工具策略版本、目标引用及版本、服务器金额、期限和人工审阅。
只有已绑定管理信封可提出请求。请求重发复用原回执；同一 key 改参数拒绝；同一信封里的
两个相同动作仍是两个不同的动作身份。Agent 不能通过参数提供批准人、确认凭据或替换入参。

提案只写等待事实，不运行业务 handler。Owner 批准先独立提交，因此在批准和执行之间崩溃后
仍可恢复。执行取得短写事务，重新核对当前 Owner、原批准人及会话、提案人身份及任职、
当前项目管理者、Authority、原决策和条款；领域服务继续校验资金与资源。原管理会话可以已经
结束，但不会被重新打开，普通 Runtime 入口仍只允许运行中的会话。

效果、最终 ToolAudit、确认终态和决策聚合共用事务。任一审计或确认落库失败都回滚效果，
保留已批准状态供重试；业务拒绝则保存明确失败。并发批准及响应丢失只能产生一次效果。
批准人或原批准会话失效也拒绝执行；更换批准人需要新的提案，不能改写历史批准。

## 回执与查询

最初的 `confirmation_pending` ToolAudit 保持 U7 不可变。批准后的执行、拒绝或过期另存最终
回执，由确认记录关联。原请求重放始终返回原动作回执；其外层 `decision_status` 按既有约定
读取当前事实，不承诺整个外层响应永远逐字相同。

等待中的决策保持 `EXECUTING / resolved_at=NULL`，不算成功或失败。按逻辑动作聚合最终结果，
不会把初始和最终两份回执算成两次动作；完整审计历史仍可查看。若 Owner 在信封第一项动作
之后立即批准，系统还会核对声明的动作总数，剩余动作未产生回执前不会提前结束决策。

最终拒绝若发生在当前 Authority 校验之前，授权结果保持未知，不能复制提案时的旧成功结论。
提案身份、参数、期限、人工决定和完成回执由 SQLite 约束及触发器保护，普通 SQL 更新同样受限。

正式资源为 `/api/v1/action-confirmations`：

| 方法与路径 | 行为 |
| --- | --- |
| GET 集合或 `/{id}` | 查询本公司事实，集合按 ID 分页，最多 100 条 |
| POST `/{id}/approve` | 当前 Owner 批准固定提案，并尝试执行 |
| POST `/{id}/reject` | 当前 Owner 拒绝尚未批准的提案 |
| POST `/{id}/execute` | 当前 Owner 恢复已批准动作，已完成时复用结果 |
| POST `/{id}/expire` | 当前 Owner 收口已到期请求；不能提前使其过期 |

所有接口要求真实 UserSession，即使开发模式没有全局强制登录。写接口另核对 cookie、header
和已存会话中的 CSRF token，JSON 请求体不接受额外字段。Agent 的
`inspect_action_confirmation / list_action_confirmations` 共用相同查询服务，只能读取本公司事实。
查询提供 `deadline_passed`，不暗中改写状态；命令和有界 `expire_due` 扫描持久化过期事实。
