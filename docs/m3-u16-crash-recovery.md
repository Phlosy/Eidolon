## 第一段：完成事件与结果同事务

旧收尾先提交会话、任务、产物和内部计算成本，随后分别保存完成事件。进程若在两者之间
退出，任务已经进入 in_review，却没有 task.review_required 来源供管理扫描发现。

普通收尾现在通过现有 EventBus.publish(db=db)，把以下既有事件放入原领域事务：

- artifact.created：每个被接纳的产物一条。
- task.in_review、task.review_required、task.completed：仅在原任务仍可推进且执行成功时保存。
- employee.status_changed：仅在释放原执行人对该任务的占用时保存。

task.blocked 原本已经与技术失败收尾同事务，本段保持其语义。事件的公司、项目、任务与
执行人字段、载荷及顺序保持原约定。task.completed 仍是既有工作完成通知，不代替正式评审；
普通成功任务保持 in_review。

广播在提交后由原事务回调尝试送达。即使进程先退出，管理侧仍可通过既有有界
management_dispatch.discover_sources 扫描持久事件，每个来源只形成一条管理派发记录。
本段没有新增通用 outbox、事件类型或自动业务决定，也没有改变管理运行器的默认开关。

事件 INSERT 失败会回滚整个收尾事务，包括产物接纳回执、Drive 数据库记录、会话与任务状态、
占用释放和本次计算成本记录。恢复存储后重试原收尾只产生一份提交结果。文件系统写入沿用
U14 规则：事务回滚可能留下未被数据库引用的字节，它们不构成被接纳产物；本段不宣称新增
文件垃圾回收。

门控的 review_fixture 保留原来的独立短事务：先收尾，再由明确标记的替身形成评审结论，
最后发布带有 verdict 对应 status / fixture_review 的通知。替身通过时不重复要求指定评审人；
没有有效替身评审时保留等待评审。这个演示路径不作为生产崩溃恢复证明。

## 第二段：已提交结果的宿主记录恢复

领域事务与 RuntimeAttempt 的宿主收尾记录之间还有一个强退窗口。已经完成的会话和
不可变产物接纳回执足以证明结果提交成功；重启后无需再次执行、收集产物或扣费。

新增 [work/recovery.py](../apps/server/app/work/recovery.py)。扫描同时要求原会话是已完成的
真实 Worker、有结束时间，且原 attempt 已完成并存在产物接纳回执，然后通过遥测唯一写入者
补齐缺失的 completed 宿主结果，原因明确记为 domain_result_recovered。已有 host_outcome
及其时间和原因保持原样，包括失败或取消。运行中会话、只写完产物的会话、缺少回执或结束
时间的会话均不被补成成功。判定基于历史来源，不依赖当前员工绑定、当前任务状态或运行年龄。

每次读取一页 WorkSession 主键范围，默认 25、上限 100，返回会话、尝试引用及处理原因。
无可修复记录的页面只读；真正写入前以短事务重新核对来源和公司范围。并发扫描只有一次
补写生效，调用方回滚不会留下半次宿主记录。现有 finish_host 复用同一个支持事务的写入者，
并拒绝请求身份所属公司之外的记录。

编排器启动时捕获已有会话 ID 上界，在原有 dispatch/sweep 循环中逐页恢复；关闭新派发时
同样生效。处理完启动时这批记录便停止扫描，后续新建会话由其原执行者负责。存储失败不会
推进游标，下一轮重新检查原页。没有新增后台服务、事件订阅或通用消息平台。

进程强退测试现已扩展：新进程先恢复管理来源，再连续两次扫描宿主记录，分别返回 repaired
和 already_recorded；原事件、产物、内部成本均不增加。另有分页及非法边界、公司隔离、
并发扫描、已有结果保留、不完整来源、读写之间来源变化、只读页不抢写锁、调用方回滚、
启动上界、关闭派发与存储故障重试覆盖。修改生产代码前，新增恢复入口尚不存在，观察到
19 项预期失败与 11 项既有行为通过；实现后首次相关回归 96 项通过，补充边界后本文件
36 项通过。完整后端与静态检查结果记录在
[第二段证据](evidence/m3-u16-committed-host-outcomes.json)。

本段不访问 Runtime 或 Provider，也不将停机时间计作运行用量。它修复的是已经提交的
领域结果对应的宿主事实，不据此宣称遗留 running 会话已经恢复。

## 第三段：保留原请求截止时间

原 Worker 与受控对话的时限只保存在进程内。新增 v63 的可空 deadline_at，在请求意图
提交时保存 UTC 截止时间。同一请求重放或显式技术重试均沿用第一条期限，不因传入新的
时限重新计时。旧记录保持 NULL；升级不会从当前员工配置、创建时间或运行年龄猜测期限。

Worker 采用原 run_timeout_seconds；管理和评审轮次采用轮次限制与当前对话剩余时间中
较小的值。请求发送前，AttemptRecorder 从数据库读取期限并核对公司和请求身份，将本次
等待限制为剩余额度。两种 Worker adapter 与受控宿主都使用该检查；过期或未知时不发出
模型请求。本次等待仍由单调时钟约束，不在每次轮询中重置时限。

期限用于限制宿主等待，不证明远端已停止，也不表示实际用量。U15 的停止意图、原 run
核对和未确认远端对后续请求的阻挡继续有效。恢复整个受控对话还需要原动作事实，不能只靠
这一列重开会话。跨进程期限依赖宿主 UTC 时钟，活动等待使用单调时钟；没有引入时钟同步服务。

SQLite 同时拒绝非法日期、修改/回填既有期限，以及同一请求的后续尝试另设期限。v63 升级
保留原记录，metadata 建库与迁移建库的守卫一致；降级若会抹去已知期限，先拒绝再返回，
不会留下部分 DDL。既有迁移测试仅更新当前 head 与新增可空列的历史兼容断言。

进程测试在准备原请求后执行 os._exit(23)。两个新进程随后分别在原期限前、原期限后读取，
即使重放时要求更长时间，仍只得到原剩余 5 秒或明确过期；原请求始终只有一条。测试时钟
位置由测试输入控制，进程退出、SQLite 提交和新进程读取使用真实实现，没有远端或付费调用。
定向检查还覆盖旧记录未知、显式重试、原始 SQL 越过写入者的反例、公司隔离，以及两种
Worker 和受控轮次过期后零发送。完整命令与结果见
[第三段证据](evidence/m3-u16-execution-deadlines.json)。

## 第四段：恢复已经批准的固定动作

现有 approve API 先保存批准，再执行动作。启动扫描现在覆盖两次提交之间的退出窗口：
按 ActionConfirmation 主键分页读取启动时已有记录，默认 25、最多 100 条，只对 approved
来源调用既有 action_confirmations.execute。执行仍使用记录中的原批准人、原登录会话和
固定参数；没有替换批准人、重新提案或请求模型决定。

execute 在短事务中重新检查活跃 Owner、原批准有效期、当前 Agent 权限、目标版本与资金。
批准人的登录会话失效或已失去 Owner 身份时，保留原 approved，扫描结果报告既有拒绝原因；
不会替用户续期或换用其他人的身份。目标、权限、资金等动作条件不满足，以及批准过期时，
沿用执行服务的失败/过期终态回执。pending 不自动批准，已有终态和最终回执保持不变。

读取普通页面只取 ID、状态与回执引用，不加载完整参数，也不取得 SQLite 写锁。确实需要
恢复时，先以短写事务重新读取原来源与公司范围，再执行原服务。存储失败抛给编排循环，
游标保持原位置；已提交的动作在下一次读取时复用终态。关闭新任务派发仍可恢复，处理完
启动时这批确认记录后停止扫描。扫描结果只含确认 ID、处理原因和最终回执 ID。

编排器现在于事件消费者注册并启动后再启动，使恢复动作产生的领域事件进入已就绪的
消费者。关闭时仍先停止生产者，最后排空事件引擎；没有新增后台服务或事件词汇。

进程测试使用真实 recruit_from_market、招聘、T2 交易、内部 credit 和回执事务。第一个
子进程保存批准后 os._exit(23)，此时无雇员、无扣款；新进程恢复，并在原动作外层事务
提交后 os._exit(24)。再由两个新进程扫描，最终始终只有一名雇员、一条待执行环境开通
意图、一次 1200 CREDIT 扣款、两条原招聘/购买事件和一份最终动作回执。开通意图保持
pending，没有启动 Docker 或进行模型调用；内部 CREDIT 不是 Provider 美元费用。

另有并发扫描、分页与启动上界、公司隔离、只读页面、来源在加锁前已完成、当前授权变化、
过期和存储故障回滚/重试的覆盖。测试与命令记录见
[第四段证据](evidence/m3-u16-approved-actions.json)。

## 第五段：续接进程退出时的原 Worker

沿用项目已声明的单后端进程部署，编排器启动时捕获 WorkSession ID 上界，按主键分页读取
其中仍 running 的真实 Worker，并接管原会话。每次扫描最多填满四个宿主协程，已由当前进程
持有的会话不接管，上界之后的新会话不属于这次恢复。关闭新派发仍可恢复；成功处理完该批
来源后停止扫描，存储失败的 owner 退回原游标位置，后续仍检查同一份来源。

[worker_resume.py](../apps/server/app/work/worker_resume.py) 只重建原连接和运行引用，不调用
create_session、send_task 或 complete_turn，不创建新 WorkSession、RuntimeAttempt 或模型
请求。身份核对沿用原 Person、公司、Runtime 版本与连接指纹。尚未保存终态的原 run 在原
UTC 期限的剩余时间内查询，活动等待使用单调时钟；running 和 unknown 均不当作失败终态。
短暂读错误复用 U15 的最多两次持久重试，不增加 task.rework_count，也不重新计时。

已经持久化的原生终态可直接复用，但产物仍须用原不可变工作目录、清单、哈希、类型要求
和会话/run 归属通过采集及领域接纳。查询后、采集后、领域提交前分别保留原身份与任务守卫；
中途取消、暂停、换绑、旧产物或不完整文件不能推进业务。完成会话的任务仍进入 in_review，
恢复程序不生成正式评审结论。Hermes 和 OpenClaw 均使用原 adapter 的查询、采集与停止接口。

原请求或 run 引用缺失、原期限未知/过期、原连接不再可信，以及无法恢复的读错误，会收尾
已失去宿主的会话为 failed，将仍 in_progress 的原任务转既有 blocked。已暂停、取消或终态
任务保持原样。有原引用时先保存停止意图，再停止并核对；无引用或连接身份不符时不猜停止
目标。原生终态未知仍保留 unknown/空 ended_at，新派发继续受 U15 限制；HTTP 404、停止
响应或本地超时均不被伪造为远端已停止。停机期间不自动改派或重规划。

恢复复用原 _finalize，把会话、任务、产物回执、内部成本、通知来源及宿主结果放进同一个
短事务；写入前检查仍是同一最新 Worker attempt。关键事实先 flush，再进入可选费用处理，
避免费用服务自己的异常处理吞掉宿主回执错误。真实 SQLite 拒绝写入时整笔事务回滚，解除
故障后重试复用已保存原生终态，得到唯一领域结果。退出时等待恢复协程及其有界远端清理。

恢复耗时保留 NULL，不能用停机时间或 0 填充。内部 credit 沿用 M1 的最低单位规则，不能
解释为 Provider 实际账单。旧按耗时生成反思/技能平均值的路径在未知耗时时不运行；当前
SkillUsage 结果仅更新原 WorkSession 的记录，先前会话的使用结果保持原样。真实用量与
成长指标仍分别由 U17 和后续工作包提供，不以这段恢复逻辑补造。

[test_m3_worker_resume.py](../apps/server/tests/test_m3_worker_resume.py) 使用实际子进程强退：
请求意图提交后、接受引用保存后、原清单写完后执行 os._exit(23)，新解释器运行真实启动
扫描与收尾；另在恢复领域外层提交后执行 os._exit(24)。后续两次重启保持原尝试、产物、
成本和通知 ID。前置测试观察到 7 项预期失败，其中发送前/接受后/清单后的强退已经发生，
但旧编排器无法恢复；实现之后才完成恢复提交后的第二个强退窗口。

本段原生传输由协议替身控制，文件、SQLite、领域、内部 credit、停止意图与进程退出使用
真实实现，没有 Docker 或付费模型调用。还覆盖期限、远端未知、原生失败、引用缺失、权限
竞争、存储回滚、历史技能归属、公司隔离、分页/并发界限及退出等待。完整命令与结果见
[第五段证据](evidence/m3-u16-running-workers.json)。

正式 ce-code-review 的范围检查要求 full 审阅，但此前已确认的代理容量限制阻止独立审阅，
本段记录为未完成；本地源代码检查和自动化测试不能代替独立审阅通过。

## 第六段：从完整回执恢复决策汇总

RuntimeOperation 逐个提交动作及其 ToolAudit，最后才汇总 DecisionRecord。进程在最后一个
动作提交后退出，可能留下效果齐全但仍为 EXECUTING 的决策。启动扫描现在捕获公司范围内
的 DecisionRecord ID 上界，按主键读取有限页面，默认 25、最多 100 条；无可修复来源的
页面保持只读。已有终态、被取代、缺少关联请求、动作回执不齐或仍待确认时，分别报告原因。

只有原 RuntimeOperation 的动作回执数量完整、逻辑动作不再等待审批的决策才进入短写事务。
加锁后重新核对原记录及来源，再调用既有 decisions.refresh_from_receipts 汇总为 APPLIED、
PARTIALLY_APPLIED 或 FAILED。确认提案与最终执行回执沿用原替换规则，一个逻辑动作只计算
一次。人物或授权后续变化不会改写已提交的历史事实；本段不调用工具、模型或远端 Runtime。

扫描不重放动作、不重新批准，也不从请求哈希推测缺失参数。存储失败不推进游标；同页
此前已提交的结果在重试时直接复用。重复及并发扫描保持原 resolved_at、Task、Operation、
ToolAudit 和 Event ID，不新增领域效果。关闭新派发时同样运行，完成启动时这批来源后停止。

[test_m3_decision_recovery.py](../apps/server/tests/test_m3_decision_recovery.py) 在真实动作事务
全部提交后、决策汇总之前执行 os._exit(23)。新的解释器只读取数据库来源，分别恢复全部
成功、部分成功和全部失败，再重复扫描验证同一结果。实施前这三种强退已经发生，连同
缺少扫描入口等反例共观察到 8 项预期失败。

共 16 项新增场景还覆盖缺动作、审批未决及批准后的最终回执、当前授权撤销、来源在加锁前
被取代、只读页面、公司隔离、上界与非法分页、并发、真实 SQL 写入拒绝及编排器游标重试。
领域、回执、SQLite 与进程退出使用真实实现；无真实容器或付费模型调用。完整命令和结果见
[第六段证据](evidence/m3-u16-decision-receipts.json)。

第五、六段代码整理分别按复用、质量和效率三个维度在本地完成，沿用已记录的代理容量

## 第七段：项目推进与通知同事务

既有 _advance 在项目和里程碑完成之后才分别保存 project.delivery_ready / project.completed。
其中公司默认工作模式提升还会提前提交整个领域事务，使进程在第一次提交后退出时，留下
已完成项目却没有任何完成通知。编排器现在以既有短写事务保护原条件判断，项目、里程碑、
公司默认值与既有事件共同提交，提交后由 EventBus 原事务回调广播。

work_defaults 的两个提升辅助函数新增可选 commit 参数，默认 True 保留既有 API 和阶段
交付调用的提交方式。_advance 显式传入 False；对应 company.work_default_changed 通知也
使用调用方事务，回滚不会保存事件或触发广播。显式配置的公司默认值保持不变，既有项目的
work_mode 快照也不改变。并发完成同一项目只产生一组完成事件；两个项目共享一次默认提升。

task.ready、project.replan_required 和 project.awaiting_management_action 仍沿用原事件
词汇、载荷、归属与判断。仅就绪不批准任务，失败不重开任务，等待评审不会被转为交付。
本段没有自动重规划、新事件或新数据表，也没有扩大项目完成条件。

[test_m3_project_advance_recovery.py](../apps/server/tests/test_m3_project_advance_recovery.py)

两次全新解释器重复调用原推进，完成事件 ID、项目模式及公司默认值保持一致。实施前两种

12 项新增场景覆盖事件拒绝时整笔回滚与重试、同项目及跨项目并发、广播只读到完整提交、
调用方提交/回滚和三类其他推进通知。边界测试曾错误断言公司没有任何事件，实际命中了

## 第八段：从已完成任务恢复项目事实

编排器现在捕获启动时公司范围内的 Project ID 上界，每页默认 25、最多 100 个项目。关闭
新派发仍扫描；完成这批来源后停止。普通页面只读取判断所需字段，只有可修复来源才取得
短写事务，重新核对项目、任务图和公司范围后处理。存储失败保留原游标，已提交的来源在
下一轮复用原结果。

正常推进和恢复共用 [project_completion.py](../apps/server/app/work/project_completion.py)。
只有任务图非空、合法且全部 Task 已经 done，才将 in_progress / in_review 项目推进为
completed，并按既有规则保存里程碑、公司默认值与两个完成通知。空图、未完成、等待评审、
暂停、取消和失败任务不能据此完成项目；requested、planning、waiting_for_management、
cancelled 和 rejected 项目也保持原状。系统不产生任务、评审结论或管理决定。

检查中发现既有 project_runtime_state 在非法图分支也可能返回 all_tasks_done。新增反例
已证明旧正常推进会把循环依赖的项目标为完成；共享服务现在要求图合法，两条路径都保留
该门禁。这是对既有 M2 图契约的修正，不是通过恢复替管理者修改计划。

对于已经 completed 且当前任务事实仍支持完成的项目，只补齐缺少的 project.delivery_ready
或 project.completed。已有事件的 ID、内容和时间保持原样，不再次提升公司默认值或改动
里程碑。补发记录使用恢复时的观察时间与当时项目名称，不推测原完成时间。新的项目完成、
既有通知补齐和所有跳过原因均有明确扫描结果。

进程测试使用既有 Task 状态服务提交 in_review → done 后执行 os._exit(23)，当时项目仍
处于原 in_progress / in_review。全新解释器只读取数据库来源，恢复完成事务后再执行
os._exit(24)，后续两个新进程扫描均保持原任务结束时间、项目模式及事件 ID。任务完成状态
是隔离测试的领域输入，这份证据验证崩溃恢复，不作为真实模型或正式评审验收。

本段在既有测试文件中增加 31 项场景，合计 43 项。除上述两个进程窗口，还覆盖四种遗留
通知组合、非法图的正常/恢复路径、全部不合格状态、空图、公司隔离、分页上界、只读页、
加锁前取消或新增任务、与正常推进并发、真实 SQL 写入拒绝，以及实际启动游标重试。修改
生产代码前观察到 9 项预期失败与 12 项原有行为通过。完整命令及结果见

## 第九段：保存原请求与受控尝试的关联

`RuntimeOperation.request_body` 保存通过既有严格协议校验的原始 JSON，最多 64 KiB。
摘要仍基于规范化后的请求，动作结果仍只来自 ToolAudit。采用原文本可以保留输入字节边界，
避免补齐可选字段后反而超限；不同空白格式的等价重传仍复用同一 operation，并保留第一次
接纳的正文。恢复读取会重新校验完整协议、摘要、kind、key 和动作数，不从摘要猜测动作。

宿主通过内部参数，将最新受控 RuntimeAttempt 的 `reply_operation_id` 一次性绑定到同一
WorkSession 的 operation。原尝试必须 completed 且有 completed / reply_received 宿主
观察，仍匹配原会话和实例，也不能已有停止意图。原意图、正文和关联共同提交，随后每个
动作仍使用原事务执行器，并再次核对来源。不同轮次可以重传同一 operation；一个尝试不能
改绑到另一个请求。模型 JSON 不能提供该关联，普通遥测也不能通过它触发动作。

v64 `64da10b82e39` 只增加两个 nullable 字段。旧行保留 NULL，既不从当前资料回填正文，也
不按时间顺序猜关联。SQL 守卫拒绝修改正文、清除/改绑已保存关联、错误来源和通过
INSERT OR REPLACE 擦除原请求。受限字段和 JSON 形状检查也覆盖直接 SQL；完整协议和摘要
由恢复读取器重验。迁移与 metadata 建表等价，有新来源事实时降级会在 DDL 前拒绝。

两组进程测试分别在意图提交后、首个动作提交后执行 os._exit(23)。恢复进程仅接收原
WorkSession ID，从数据库读取正文与关联，再经原 bridge 执行缺少的动作；第二个动作提交
后再次 os._exit(24)，随后两个新进程保持原 ToolAudit、Event 和领域对象 ID。这里验证的是
持久来源和原 bridge 的复用，自动会话接管仍在后续实现；隔离的协议替身不算真实 Runtime
或模型验收。

新增 35 项来源场景与 2 项迁移场景。覆盖读/决定/finish、跨轮重传、停止与来源换代、跨会话、
错误 ID、未接纳输出、动作额度、原子回滚、SQL 改写、正文缺失/损坏，以及精确 64 KiB 输入。
修改生产代码前观察到 4 项预期失败，包括真实强退后的来源缺失；随后 200 项 bridge/会话
测试通过，边界和迁移组合 41 项通过。命令及最终回归结果见
[第九段证据](evidence/m3-u16-request-sources.json)。

最终完整后端回归为 3126 passed / 26 deselected，118 条既有告警；Python lint、553 个文件
的格式检查（含本次迁移）以及前端 TypeScript / ESLint 均通过。首次全量的两个历史夹具
失败已保留：v60 显式验证新增关联为 NULL；v57 使用正文从未采集的历史请求，继续验证其
自身的审批历史保护。修正后相关迁移 8 项通过，再次全量通过；生产行为未因此修改。

三个代码整理维度均完成，无额外修改；保留迁移的历史 SQL 定义及逐动作来源重检。新代理
