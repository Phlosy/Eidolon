# M3 U16 崩溃恢复

状态：实施中。第一段修复普通 Worker 领域提交后的通知来源缺失；尚未完成整个 U16。
实现依据为 [M3 计划 U16 / KTD8](m3-implementation-plan.md) 与
[M2 兼容增补登记](m2-freeze.md)。U14 的真实整链以及 U15–U17 的联合验收仍保持待办。

## 第一段：完成事件与结果同事务

旧收尾先提交会话、任务、产物和内部计算成本，随后分别保存完成事件。进程若在两者之间
退出，任务已经进入 in_review，却没有 task.review_required 来源供管理扫描发现。

普通收尾现在通过现有 EventBus.publish(db=db)，把以下既有事件放入原领域事务：

- artifact.created：每个被接纳的产物一条。
- task.in_review、task.review_required、task.completed：仅在原任务仍可推进且执行成功时保存。
- employee.status_changed：仅在释放原执行人对该任务的占用时保存。

task.blocked 原本已经与技术失败收尾同事务，本段保持其语义。事件的公司、项目、任务与
执行人字段、载荷及顺序保持原约定。task.completed 仍是既有工作完成通知，不代替正式评审；
普通成功任务保持 in_review。

广播在提交后由原事务回调尝试送达。即使进程先退出，管理侧仍可通过既有有界
management_dispatch.discover_sources 扫描持久事件，每个来源只形成一条管理派发记录。
本段没有新增通用 outbox、事件类型或自动业务决定，也没有改变管理运行器的默认开关。

事件 INSERT 失败会回滚整个收尾事务，包括产物接纳回执、Drive 数据库记录、会话与任务状态、
占用释放和本次计算成本记录。恢复存储后重试原收尾只产生一份提交结果。文件系统写入沿用
U14 规则：事务回滚可能留下未被数据库引用的字节，它们不构成被接纳产物；本段不宣称新增
文件垃圾回收。

门控的 review_fixture 保留原来的独立短事务：先收尾，再由明确标记的替身形成评审结论，
最后发布带有 verdict 对应 status / fixture_review 的通知。替身通过时不重复要求指定评审人；
没有有效替身评审时保留等待评审。这个演示路径不作为生产崩溃恢复证明。

## 故障证据

测试位于 [test_m3_recovery.py](../apps/server/tests/test_m3_recovery.py)。Runtime 结果使用
固定测试输入；归属检查、产物接纳、规范字节、成本服务、SQLite 事务及管理发现均使用真实
实现与隔离数据库。本段没有真实容器或模型调用，也没有 Provider 费用。

进程测试在原收尾外层事务的 SQLAlchemy after_commit 钩子中执行 os._exit(23)，跳过
内存事务回调及正常清理。成本服务的 SAVEPOINT 提交不触发强退。父进程核对会话已 completed、
任务仍 in_review、规范产物字节一致、内部 credit 成本记录存在，五类完成事件均已持久化。
随后新进程连续扫描两次，再重放原收尾；事件 ID、产物与成本记录不变，评审通知只对应一条
待处理管理派发。这是强制进程退出证据，未以正常 Ctrl-C 或抛出可捕获异常代替。

实施前观察到五项事件存储反例失败。进程测试最初有一处 Currency 大小写断言错误，修正为
仓库枚举后，在未修改生产代码时明确复现“五类完成事件全部缺失”。原始失败日志保留。
补充覆盖五个 INSERT 拒绝点及恢复重试、并发收尾与提交后广播可见性、两种替身评审结果、
技术失败时三个行政任务状态，共 12 项。

完整命令、结果、日志摘要与源文件摘要记录在
[第一段证据](evidence/m3-u16-completion-events.json)。相关 M1/M2 冻结锚点与跨层回归随该证据
记录；跳过或未运行的真实环境检查不计入通过。

## 后续边界

本段保证新普通收尾的通知来源不会与领域结果分离。既有历史缺失事件的补偿、远端会话与
旧进程持有者恢复、确认后动作续接、Evidence / 反思 / 项目推进等后续效果的扫描、启动顺序
和更多强退窗口仍属 U16 后续工作。管理来源被发现不代表模型已经执行决定；不会因此补写
评审通过、重规划或把未知远端状态当作停止。
